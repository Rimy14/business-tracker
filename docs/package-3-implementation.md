# Package 3 implementation notes

## Data contracts

- Monetary records keep the original numeric amount and use `currency: "LKR" | "USD"`.
- Existing records without `currency` are interpreted as LKR.
- Booking income uses `source: "Room Revenue - Booking"`, `bookingId`, `currency`, and `bookingChannel`.
- New and edited paid bookings use deterministic income IDs (`booking_<bookingId>`); edits migrate legacy duplicate income records into the canonical document.
- Restaurant orders are stored in `restaurantOrders` and linked income uses `source: "Restaurant"`, `restaurantOrderId`, and `isAutoGenerated: true`.
- Restaurant income document IDs are deterministic (`restaurant_<orderId>`) to prevent duplicates.
- Supplier tax details use the optional string field `tax`.
- The shared USD/LKR cache is `settings/exchangeRate`.

## Exchange-rate behavior

The browser reads the Firestore cache first. A rate younger than 24 hours is reused. When the cache is stale or missing, the application fetches `https://open.er-api.com/v6/latest/USD`, validates the LKR rate, and writes it back to Firestore. If the provider fails, the last valid cached rate is returned with a stale indicator. If no valid rate exists, original currency values remain visible and conversion is not fabricated. Cross-currency totals and report cells show an unavailable marker (`—`) rather than adding or relabelling incompatible amounts.

## Restaurant payment invariant

- Pending order: no income document.
- Pending to paid: linked income is created.
- Paid order changes: linked income is updated.
- Paid to pending: linked income is removed.
- Deleting an order: linked income is removed.

Order and income mutations use one Firestore batch.

Booking, linked income, and affected room-status mutations also use one Firestore batch. Paid booking edits synchronize amount, date, currency, booking channel, and description even when the total amount is unchanged.

## Output safety

Stored finance descriptions, sources, creator names, supplier tax values, and restaurant text are HTML-escaped before being inserted into rendered tables or ledgers.

## Package 1 and Package 2 integration

- Manager-side locked controls use the provisional `data-requires="manager"` and `data-requires="report-download"` markers. Align these with Package 1's final permission helper during merge.
- Package 2 owns booking form markup. Package 3 reads `bookingCurrency`, `bookingChannel`, and their edit/custom counterparts when present, while defaulting legacy/current bookings to LKR.
- If Package 2 renames the booking page or input IDs, move the Package 3 report/conversion hooks to the final `bookings.html` without changing the stored `currency` and `bookingChannel` field names.
